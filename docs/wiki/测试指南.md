# 测试指南

[返回文档中心](Home.md)

测试应回答具体问题：核心数字是否正确、正式启动是否隔离、界面是否可读、当前机器是否接通真实来源、安装后是否运行目标产物。这些结论需要分别取得证据。

## 测试层次

| 层次 | 命令或方式 | 能说明什么 | 不能说明什么 |
| --- | --- | --- | --- |
| 核心检查 | `swift run --force-resolved-versions TokenStatCoreChecks` | 合成记录、协议、窗口、继承和安全边界符合断言 | 真实企业账号或当前 UI 可用 |
| 原生测试 | `swift test --force-resolved-versions` | App 状态、偏好、专用启动和界面相关回归 | 所有 OS 上的视觉一致或真实权限行为 |
| 隔离集成 | `./script/test.sh` | 核心、构建与独立 App 子进程的启动/保存/重载契约 | 默认后台真的接通 Hub |
| 离线预览 | `python3 script/render_preview.py` | 实际 SwiftUI 视图可用合成数据渲染，供人工检查 | 正式 App 已有对应真实来源 |
| 合成性能基准 | `python3 script/benchmark_menu.py` | 同编译配置与合成输入下，比较指定菜单热路径的耗时和发布次数 | 整 App CPU、RSS、真实网关或持续采集负载 |
| Release 校验器 | `python3 -B script/test_release_assets.py` | 当前四资产历史与下一版五资产 DMG 的标签/版本/摘要/路径拒绝、只读镜像和原生包装 fixture 契约 | GitHub Actions 已实际发布或下载产物已经安装 |
| Homebrew 包装 | `brew test Tupig/tokenstatmenu/tokenstatmenu` | 已安装 Formula 的 Bundle、主机架构、图标、来源、签名与启动器 | GUI、企业连接、Intel 实机或 Apple 公证 |
| 真实本机验收 | 正常无隔离参数启动，人工检查来源与时效 | 当前环境的实际数据链路、菜单栏及重启恢复 | 全新机器分发、所有企业部署或 Intel 实机都通过 |
| 发布产物验收 | 核对安装路径、版本、源码身份、二进制与签名 | 被测试、安装、发布的产物一致 | Apple 公证、真实来源等其他未做项目自动通过 |

## 运行核心与原生检查

在项目根目录中运行：

```bash
swift run --force-resolved-versions TokenStatCoreChecks
DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer swift test --force-resolved-versions
```

核心可执行检查使用合成数据，不调用真实企业网关。原生测试包含纯状态检查、真实 SwiftUI/NSHostingView 渲染和视觉相关检查。系统字体、系统版本、显示比例与渲染环境会影响像素比较，不能把环境差异自动接受为新基线。

SwiftPM 使用工具链默认构建系统，不添加已弃用的 native 模式参数。当前命令统一使用 `--force-resolved-versions`，依赖精确锁缺项或冲突时失败，不能靠删除锁或在构建后恢复它来通过检查；两种工具链图和本机/CI边界见[编译指南](编译指南.md#固定测试依赖与跨工具链锁)。若 CLT 默认引擎出现缺失搜索路径的 linker warning，参考[工具链诊断](编译指南.md#clt-默认构建的已知工具链警告)；完整 Xcode 的逐命令选择不改变全局开发目录，构建成功也不意味着 CLT 警告已修复。

需要缩小到某类测试时：

```bash
DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer \
  swift test --force-resolved-versions --filter SeasunStartupContractTests
DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer \
  swift test --force-resolved-versions --filter TokenHubQuotaStateTests
```

同一个 `.build` 目录不要并发运行多个 SwiftPM 构建。确需独立并行时，为每条任务选择不同的 `--scratch-path`，并在报告中记录各自的命令与目标；不要让测试等待被误判为卡死。

### 并发与金额边界回归

`TokenHubQuotaStateTests` 使用可控异步替身与合成记录，检查本地缓存和原生 AX 两个独立 actor 边界：

- 本地 worker 冷读、暖缓存、generation 重建、并发请求串行化，以及路由变化后拒绝复用其他来源摘要。
- 重载期间不重叠本地读取，旧结果不发布，完成后恢复至少 5 秒的刷新调度；关闭后迟到结果与资源计数收敛。
- AX 请求待完成时主 actor heartbeat 仍可运行，最多一个扫描；未授权真实 worker 在发现进程或读取 AX 前返回权限不足。
- 关闭兼容读取、撤销信任、切换模式、退出及 Hub 重启后丢弃旧 AX 结果；旧 AX 不能覆盖较新的直接来源，也不能释放新一代直接请求的进行中标记。
- 原生/合成来源标记经闭包包装后仍可区分，fixture 不会因依赖注入而意外读取真实界面。

这些断言不能证明已运行真实的 AX 正向扫描。Core 中的合成 reader 另行覆盖允许属性、唯一身份、双读、节点/字符/时间预算。

`DirectQuotaChecks.swift` 从实际公开 decoder 入口验证滚动窗口和月度已用/上限四种字段上下文。金额只接受完整 JSON number 语法、最多 128 个 UTF-8 字节和保守 38 位有效尾数；垃圾后缀、空白、逗号、不完整指数、布尔、必要 null、负值、非有限、溢出和精度丢失应被拒绝，合法小数、指数、零和边界仍保留。月度可选 null 上限单独覆盖。原生 JSON number 经 Foundation 规范化的限制见[实现范围](../IMPLEMENTATION.md#hub-企业额度)，不能将该测试解释为任意精度 JSON 原文保真。

## 运行隔离启动集成

```bash
./script/test.sh
```

脚本依次运行核心检查、`--build-only` 和 `script/integration.py`。集成使用临时偏好文件和独立子进程，并通过 `--disable-background-services` 关闭本地扫描、Hub 直接读取、辅助功能读取、观察者及计时器。退出清理仅针对测试持有的进程，不按全局进程名终止用户应用。

它验证无配置、旧配置、损坏配置、允许偏好、保存/重载及测试资源边界。**后台被关闭的成功启动，不能当作默认自动接入成功。** 诊断字段是布尔值与资源计数，不是数值统计来源。

## 视觉与可访问性检查

```bash
DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer \
  swift test --force-resolved-versions --filter TokenStatUISnapshotTests
python3 script/render_preview.py
```

预览图写入被忽略的 `dist/previews/`，使用合成数据而不是截取用户屏幕。部分历史核心/代理状态会出现在离线预览中，这是测试覆盖，不表示正式设置允许启动代理。

应分别检查浅色与深色外观、对齐与留白、文字是否截断、设置与退出按钮是否一致、未知与过期是否清楚。受控像素基线覆盖合成工具栏；`DashboardHistoryTests` 另行渲染实际概览共享内容，使用互相冲突的虚构企业/本地窗口，检查历史默认折叠、展开图高度及模型/I/O守恒。四张完整 460 点浅/深色图写入私有临时目录，用于独立人工检查企业主卡、历史辅助区、文字/重置时间和对称边距，不将真实用户截图提交为基线。

```bash
DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer \
  swift test --force-resolved-versions --filter DashboardHistoryTests
```

这组测试比较初始折叠/展开的实际渲染状态，没有执行原生 disclosure 点击，不自动证明焦点或 AX 文本暴露。完整页面渲染、OCR、可访问性树、自然键盘焦点和真实点击各自有不同覆盖范围。

异步 Hub Dashboard/额度卡片测试先 display/layout，再以可取消 `Task.sleep` 让出主 actor，恢复后重新布局并检查真实位图、PNG 尺寸和非空输出；每个窗口都有 `defer` 清理。不要在异步测试中用同步 RunLoop 等待替代这一让出过程；同步预览工具的实现另行处理。

[Issue #33](https://github.com/Tupig/TokenStatMenu/issues/33) 跟踪实际原生 Settings 辅助功能文字暴露。独立的私有 XCUITest 工程仅面向固定、无真实数据的已校验 fixture；本机已解锁且 build-for-testing 成功，但 test-without-building 在 runner 初始化时报 `Timed out while enabling automation mode`，退出 65，A01–A07 测试体均未执行。当前阻塞是自动化运行环境，不能报告 App AX 成功或失败，也不能用 OCR、离屏 getter 或源码标签关闭问题；没有通过修改 TCC、重置权限或降低断言绕过它。

若维护者有同一份私有 C27 fixture，可用仓库内包装器复现并分类结果。它要求当前命令显式设置完整 Xcode，先执行 `build-for-testing`，再执行 `test-without-building`；只输出构建/测试退出码与 `passed`、`test_failed` 或 `automation_environment_blocked`，原始日志和 result bundle 留在临时目录并在退出时清理：

```bash
DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer \
  ./script/run_settings_ax_check.sh \
  --project /path/to/private/C27SettingsAX.xcodeproj \
  --scheme C27SettingsAX \
  --fixture-manifest /path/to/private/preparation-manifest.json \
  --fixture-bundle "/path/to/private/TokenStatMenu AX Synthetic Fixture.app"
```

占位路径只代表维护者本机的私有 fixture，不应写入仓库、Issue 或发布包。脚本同时校验冻结 manifest、Bundle/测试源 hash、签名和单一通过的 xcresult；自动化初始化超时必须保持非零退出，A07 的 ownership/teardown 由同一固定测试方法的通过结果覆盖。脚本的分类结果不能把环境阻塞转换成 AX 通过。

基线生成环境、显式录制命令与接受规则见 [UI 测试说明](../UI_TESTING.md)。录制会生成图像并按设计失败；生成文件不等于审查通过。不要为了变绿无条件覆盖基线。

阶段 2 的脚本合同自测：

```bash
python3 -m unittest script/test_phase2_diagnostics.py
python3 -B script/diagnose_swift_toolchain.py --toolchain both
```

工具链诊断在仓库外复制受控源码到临时目录，运行最小 Hello 和当前 SwiftPM 产品构建，保留工具链类别、版本、warning 分类、退出码和 `Package.resolved` 摘要；不输出原始路径或日志，不修改 SDK、全局 `xcode-select` 或锁文件。

## 默认自动接入的本机验收

以下检查需要本机已正常运行、已登录的 Hub，不把真实返回或截图加入仓库：

1. 从已确认的 App 路径正常启动，不加后台禁用或测试数据参数，也不创建配置文件。
2. 首次异步读取结束后，确认企业来源状态、5 小时、7 天、重置时间及月度字段；来源缺失字段应保持未知。
3. 关闭可选界面兼容读取，确认直接来源继续可用，且无新的系统权限请求。
4. 正常退出并重新打开 Hub，确认旧快照失效后自动恢复；不把旧请求返回作为新实例数据。
5. 产生正常 Codex 活动，检查新鲜事件出现时的实时估算；事件停止 15 秒后不继续标成实时。
6. 确认本地 Token 小计与 Hub 金额各自标明来源，不把本地历史窗口当企业当前额度。
7. 确认菜单栏条目可见、面板可打开/关闭，正常退出后只结束 TokenStatMenu。

验收报告记录版本/构建号、测试范围、成功/失败、非敏感状态与布尔就绪信息。无新鲜活动事件时应记录实时未验证，不能用上轮均速替代“实时已通过”。

## 提交与发布前的公开内容检查

```bash
python3 script/package_source.py
python3 script/check_docs.py --self-test
python3 script/check_public_content.py
git diff --check
```

在审阅并暂存计划提交的文件后，再检查**精确暂存内容**：

```bash
python3 script/check_public_content.py --git-index
```

默认模式检查工作区白名单文件；`--git-index` 检查暂存 blob，二者不能互相代替。通过扫描也不能取代人工核对差异与来源。不得提交真实配置、凭据、企业地址、账号、额度、会话正文、运行日志或屏幕截图。

验证完成后再推送。记录应指出实际运行的命令、结果及未验证范围；历史 [验证记录](../VALIDATION.md) 不能证明当前改动已通过。

## Release 与 Homebrew 的验收顺序

Release 合成检查使用临时虚构文件和注入 HTTP，不访问真实企业网关。原生 fixture 只用于验证包装规则；不将它当作正式签名、公证或运行时测试。

```bash
python3 -B script/test_release_assets.py
```

本地全部检查、公开白名单和独立审查通过后，再推送正式标签。随后分别核对 Actions 构建/发布结果、远端当前版本四资产或下一版五资产的实际字节与 manifest/SUMS、源码包能否构建，以及 App 实际安装/启动。草稿存在、上传步骤通过或本地 ZIP/DMG 的 hash 一致都不能单独完成端到端验收；CI 与本地归档时间可能不同，最终摘要以实际发布资产为准。

tap 还应先用真实审核源码的两个版本做隔离 `brew install` / `brew test` / `brew upgrade`，保留手工 App、偏好与原运行实例，不使用覆盖或自动杀进程选项。这里的本地 URL 适配只验证 Homebrew 行为；第一份 production Formula 必须来自实际正式 Release，不能发布虚构 pin。真实公开源码下载、最终 Formula 安装和 tap Actions 结果仍需单独验证。

Homebrew 的包装测试不会启动 App，默认合成测试中跳过的显式本机安装校验也不是通过。详细配方和三个 job 的先测试后写入机制见 [CI/CD](CI-CD.md) 与 [tap 文档](https://github.com/Tupig/homebrew-tokenstatmenu#readme)。

DMG 的本机验证使用独立临时 staging/output 目录，调用 `hdiutil imageinfo`，再以 `-readonly -nobrowse` 挂载到自有临时目录，核对根目录只有 `TokenStatMenu.app` 和指向 `/Applications` 的别名，复用 App 版本、来源、四文件树、arm64/x86_64 和严格签名断言，最后只卸载该次挂载。它不会启动 App、替换用户 App、读取偏好或 Hub/Codex 数据，也不请求权限。镜像可挂载不等于安装或运行验收；下一版正式 Release 的五资产下载、空目录核对、Homebrew 更新和 Finder 拖拽仍需独立记录。

性能基准的场景、重复方法与数值解释见 [性能与基准](../PERFORMANCE.md)。不要把合成循环的下降比例写成整 App CPU 或内存下降比例。
